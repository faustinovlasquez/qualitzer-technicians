# Infraestructura offline móvil

## Integración vigente

El núcleo está conectado en [../../App.tsx](../../App.tsx) y [../application/useTechnicianApp.ts](../application/useTechnicianApp.ts), con dashboard/sucursal, detalles, centro offline, AppState y NetInfo. Las dependencias SQLite/NetInfo están declaradas en [../../package.json](../../package.json). HTTP/demo y rutas gateway están implementados; no son bloqueantes de integración pendientes. Guía de usuario y límites: [../../docs/OFFLINE.md](../../docs/OFFLINE.md).

Exports públicos desde [index.ts](index.ts):

- `createOfflineRepository(remote, session, gatewayUrl | options): Promise<OfflineTechnicianRepository>`; `options = { gatewayUrl, storageKey?, store?, fileStore?, connectivity? }`. Una instancia por sesión/sucursal. El gateway es obligatorio: un storageKey por sí solo no identifica el origen.
- `saveOfflineProfile(session, gatewayUrl): Promise<void>` **sólo después de un `remote.me()` online validado**, nunca con un perfil de caché. Debe ejecutarse antes de crear/arrancar el decorador en login normal. La creación del decorador no afirma una verificación online.
- `restoreOfflineProfile(stored): Promise<{ user, verifiedAt } | null>` valida el perfil local y también sirve a comprobaciones internas de identidad. Para restaurar la sesión como alternativa al acceso remoto, usar `restoreOfflineSession(stored, error)`: admite **sólo `NetworkError`**, nunca 401/403/404/503 ni cualquier error genérico.
- `establishVerifiedOfflineSession(repository)` consulta `remote.me` y comprueba usuario, worker, tenant y sucursal antes de desbloquear cola y escribir pasaporte. Utilizar después de reautenticarse, no limpiar la cola para solucionar un 401.
- `disableOfflineProfile(stored)` antes de eliminar sesión local o cambiar de principal. El decorador lo hace en `logout()` y en 401; el hook también lo conecta a su cierre mediante repositorio remoto y a la invalidación de sesión.
- `isOfflineQueuedError(error)`, `OfflineQueuedError`, `OfflineUnavailableError`, `OFFLINE_LIMITS`, `OFFLINE_PROFILE_MAX_AGE_MS`.

API estable de cada decorador:

- `getSnapshot()`, `subscribe(listener)` (compatible con `useSyncExternalStore`). Snapshot: `online`, `preparing`, `syncing`, `authBlocked`, `pending`, `conflicts`, `lastSyncedAt`, `lastError`, `cachedAt`, cobertura diaria y operaciones con estado/recibo/mapeo.
- `start()` / `stop()` idempotentes; el hook conecta `setForeground(active)` a visibilidad y acceso desbloqueado, y detiene la instancia anterior antes de sustituir sesión/sucursal. La sincronización automática requiere conexión, sesión válida y app abierta en primer plano y desbloqueada. «En segundo plano» respecto de la UI no significa un servicio del SO: no hay daemon ni garantía después de cerrar/deslizar la app.
- `syncNow()`, `retry(operationId)`, `hasPendingChanges()` (busca **todas** las namespaces), `readLocalFile(fileId)`.
- `prepareWeek(range, branchId, options?)`: máximo 7 fechas; guarda snapshots diarios, catálogo combinado sin `kind`, página 0 de equipos y especialidades, archivos y comentarios página 0 de hasta 30 trabajos, archivos de pasos y de hasta 30 grupos. Concurrencia de trabajos 2. Los grupos se consultan con el día de planificación, no con toda la semana. Las páginas/búsquedas de catálogo posteriores se cachean por consulta exacta: no se inventa un catálogo completo.
- Opción explícita `{ byteBudget, downloadAttachment(attachment, scope, remainingBytes): Promise<LocalPhoto> }`. El integrador descarga con autenticación sin persistir headers/tokens y debe respetar/cancelar al superar `remainingBytes`; después se copia a almacenamiento offline y comprueba tamaño real. Sin esta opción **no se descargan bytes remotos**. Metadata `offline.downloaded=false` evita presentar URL remota como disponible sin red. IDs descargados se resuelven tras reload mediante `readLocalFile`.

**Cableado actual:** login online guarda el perfil después de verificar `me` y crea el decorador. En arranque frío `restoreCachedSession` sólo se invoca ante `NetworkError`, usa el perfil ligado a la sesión live guardada y conserva `verifiedAt`; nunca inventa autorización remota. La preparación inicial automática sólo consulta asignaciones de la semana actual y catálogo combinado, una vez por instancia disponible. `prepareOfflineWeek` amplía la copia mediante acción explícita; llama a `prepareWeek` **sin downloader ni presupuesto de bytes**. La UI advierte «datos y metadatos; no descarga fotos remotas».

### Resultados de escritura y UI

`createRecord`, `addComment`, `answer`, `upload`, `uploadDocuments`, `uploadGroupFiles`, `status` para iniciar/pausar/reanudar y `attachChecklist` primero persisten, incluso con conexión. La UI no espera un envío ni una recarga remota para reconocer el guardado local. Si la operación registrada aún no está aplicada, devuelven **`OfflineQueuedError` después del commit durable**; no es un fracaso de guardado local. El motor envía y concilia por separado.

El resultado contiene `operationId`, `operationIds` (todos los documentos del lote), `kind`, `localGroupId`, `localWorkId`, `date`, `ownsFiles`. La UI puede soltar su borrador temporal de archivos **únicamente** cuando `ownsFiles=true`, o tras éxito confirmado. Nunca mostrar “guardado en servidor” con este resultado. La UI integrada muestra pendiente y permite abrir el recurso local. El centro muestra texto/respuesta/base/recibo para revisión; no implementa edición resolutiva, merge automático ni exportación de conflictos.

`assignments()` superpone creaciones con IDs `local-UUID`, su fecha/horario original, sin tiempo ejecutado inventado, sin checklists inventados, `canExecute=false`, `canEditDefinition=false`, `canManage=false`. Después del recibo usa IDs canónicos pero mantiene la ficha transitoria hasta aparecer en la lectura remota; evita duplicado por group/work. Metadata tipada en [../domain/offline.ts](../domain/offline.ts). App conecta detalles canónicos, identidad estable del borrador y estado offline al dashboard; la UI distingue evidencia pendiente de confirmada sin habilitar ejecución por adjuntos locales. Respuestas/comentarios pendientes se consultan desde `snapshot.operations`, no se hacen pasar por confirmados en las lecturas.

Las respuestas nuevas conservan `operation.answer` y `operation.base` en formato UI. El sobre persistido `operation.wire = { answer, base }` contiene exclusivamente valores canónicos de `toSyncAnswer` y `syncAnswerFromStep`; sólo ese sobre se envía. La decodificación v1 migra usando el tipo del paso cacheado sin sustituir el base original por un valor remoto posterior. Si no puede determinarlo, conserva el payload y mantiene `needs_review`, sin reset ni retry ciego. La unión de tipos sigue admitiendo operaciones canónicas preexistentes.

La agenda devuelve los días conocidos aunque falten otros del rango. `snapshot.coverage` sólo contiene fechas realmente consultadas; `snapshot.missingDates` identifica fechas faltantes del último rango solicitado, incluso cuando contienen creaciones locales. Dashboard y centro reciben esta cobertura parcial. Sin días conocidos ni creaciones locales se mantiene `OFFLINE_CACHE_MISS`.

Archivos y comentarios usan identidad sucursal/grupo/trabajo/paso o página, independiente del rango de fechas, dentro de la misma namespace. Las consultas online siguen enviando el scope original para autorización fresca. Un 403/404 conocido queda registrado y prohíbe fallback posterior hasta una lectura remota exitosa. Los JSON cacheados se validan con esquemas sin dependencias nativas ni imports del gateway.

Los adjuntos confirmados se enlazan únicamente por `receipt.fileId`; el listado canónico conserva su ID/nombre y recibe la URL de la copia local. Las vinculaciones quedan en `state.attachments`. El backend actual devuelve el ID exacto mediante callbacks posteriores al commit; un recibo histórico sin ID no autoriza adivinar vínculos y el backend lo presenta para revisión. El cliente conserva bytes de recibos legacy aplicados sin ID, sin añadir otra fila confirmada ni enlazar por nombre; puede leerlos con `readLocalFile(operation.file.id)`. No hay expulsión automática de archivos.

`status` para `completed`/`delivered`, `report`, `deleteFile`, `deleteGroupFile`, `startOrder` y `deliverOrder` requieren conexión y recurso canónico. No se encolan ni se simulan finalización/entrega. El reporte legacy no se convierte silenciosamente en comentario. Notificaciones de escritura siguen online-only. Lecturas remotas fallidas usan caché **únicamente** en `NetworkError`; señales sin red evitan el intento. 401 bloquea; 403/404/503 y JSON inválido jamás devuelven caché como si fueran éxito.

### Cronómetro y asociación de checklist

Ambas intenciones exigen un trabajo canónico único, `canExecute`, no finalizado/entregado, copia del día exacto consultado, técnico/sucursal coincidentes y ausencia de revocación conocida. El rango es diario; un trabajo atrasado visible ese día no exige que su fecha de planificación coincida. Los recursos `local-*` no habilitan estas acciones. El servidor vuelve a autorizar al aplicar.

- `timer`: iniciar/reanudar (`in_progress`) o pausar (`paused`), con `baseStatus`. La cadena conserva UUID, base y dependencia; una operación conflictiva o en revisión detiene sus dependientes. El reloj es el del servidor **al aplicar**, no al tocar: inicio y pausa enviados juntos pueden contabilizar cero segundos. No se reconstruye tiempo offline ni se extrapola el reloj pendiente.
- `checklist`: plantilla existente con `checklistId` positivo, disponible en una página del catálogo cacheada para el mismo trabajo/fecha/sucursal. No inventa un catálogo completo, pasos, respuestas ni avance; el Backend valida plantilla y relación al aplicar.
- `applied` prueba el recibo, no que la ficha mostrada esté actualizada. Para reconciliar timers, el repositorio captura los IDs ya aplicados en almacenamiento durable **antes** del GET diario y conserva esa prueba con el snapshot/caché (`offlineTimerRead`). Ni `generatedAt`, ni la hora local, ni el recibo aislado sustituyen esa causalidad. Una lectura autoritativa posterior prevalece; la UI distingue estado solicitado, confirmación y espera/error de actualización.
- Respuestas, asociaciones y evidencias pendientes no suman progreso confirmado ni habilitan una entrega ficticia. Archivos e historial se actualizan separadamente al recibir confirmación; el guardado local no espera esa recarga.

## Durabilidad, aislamiento y política de sesión

- Namespace: modo + gateway normalizado + tenant id/origen/entorno + user + worker + sucursal + SHA-256 del storageKey opcional. El storageKey no debe contener token ni credenciales. Se guarda JSON versionado con revisión; JSON corrupto falla cerrado, no reinicia/borrar la cola.
- Android/iOS: SQLite WAL, synchronous FULL, escrituras serializadas y `withExclusiveTransactionAsync(tx)`, comparación revisión dentro de transacción. Archivos UUID en `Paths.document/offline`, `await File.copy`, SHA-256 de bytes mediante `Crypto.digest`.
- Web: IndexedDB nativo, compare/write dentro de una única transacción readwrite. Blobs reales persistidos, nunca sólo blob URLs. URL de presentación se rehidrata por ID y se revoca en stop. No se importa SQLite en el bundle web; no requiere COOP/COEP/WASM.
- En web la selección previa a **Guardar archivos** es temporal; la durabilidad empieza al transferir bytes y confirmar la cola. SQLite/caché/archivos no están cifrados por la app; SecureStore/cookie protegen el token, no el contenido operativo sensible.
- 25 MiB por archivo, 500 MiB total para todas las identidades. Cuota global de blobs web en la propia transacción; reserva global nativa antes de copiar. Rechazar lleno conserva lo anterior. No expulsar pendientes. Caché JSON independiente: 180 entradas / 16 MiB (estimación UTF-16 conservadora).
- Archivo copiado antes del commit de la cola. Fallos normales de lote limpian únicamente copias no comprometidas. Una muerte del proceso entre reserva/copia/commit puede dejar una reserva/copia huérfana: se conserva conservadoramente, no se borra automáticamente, no se descuenta capacidad incierta. No se promete protección contra desinstalación, borrado manual del navegador, modo privado, fallo físico o cuotas del SO.
- Los archivos aplicados se conservan para lectura offline; no hay expulsión ni limpieza automática de recibos. Alcanzar cuota exige una futura limpieza explícita y segura de archivos confirmados, nunca borrar pendientes. La cola no se vacía al logout.
- Pasaporte: perfil User allowlisted con metadata de presentación opcional, SHA-256 del token opaco + gateway + tenant exacto. Token crudo sólo llega en memoria al hash; no se guarda en SQLite/IDB. Un índice por token+tenant, no por sucursal, para invalidar todas sus sucursales al logout/401. En web `cookie-session` **no demuestra autenticación**: el pasaporte sólo recuerda el último principal verificado en este navegador, y debe deshabilitarse al logout/rechazo conocido. Después de cambiar principal no reusar la instancia anterior.
- Sin TTL arbitrario de 7 días: `OFFLINE_PROFILE_MAX_AGE_MS = null` conserva acceso local hasta rechazo/logout conocido. Se puede configurar `maxAgeMs` al restaurar; el padre muestra `verifiedAt`/edad, no una fecha de autorización inventada. No se usa el pasaporte para autorizar escrituras remotas: cada ciclo revalida `me` y pertenencia actual antes de enviar.

El hook bloquea logout si hay pendientes en cualquier namespace y cambio de sucursal si la actual tiene operaciones sin confirmar; no ejecuta limpieza destructiva de pendientes. Un 401 detiene/invalida el perfil conservando cola; reautenticar la misma cuenta/ámbito permite revalidar y reanudar. Otra cuenta no toma posesión automática de un namespace pendiente incompatible.

## Motor y contrato remoto implementado

`OfflineEngine` sólo depende de puertos inyectados, reloj/UUID inyectados; no importa Expo/React Native. Lease durable de 240 s, dueño UUID por ciclo, hasta 30 operaciones por ciclo, recibos antes de reenviar comandos/documentos, replays de creación con mismo `clientRequestId`, backoff 2 s–5 min mientras activo. NetInfo aporta **sólo señal de enlace**; no SSID ni prueba de Internet pública. Un ciclo usa `me` de la pasarela propia para verificar alcance real.

El puerto sigue tipado opcional en `TechnicianRepository extends Partial<OfflineSyncPort>`, pero HTTP y demo actuales implementan sus tres métodos. Una implementación sin puerto no activa fallback legacy:

- `offlineCommand({operationId, kind: "comment"|"answer"|"timer"|"checklist", scope: WorkScope, payload})` → POST `/api/offline/commands`. Payload comentario `{text}`; respuesta `{stepId,answer,base}`; timer `{status,baseStatus}`; checklist `{checklistId}`. Timer/checklist exigen `workId`. El `base` canónico de respuesta se deriva del snapshot **del servidor**, con `syncAnswerFromStep`, nunca del borrador local.
- `offlineReceipt(operationId, companyBranchId)` → GET `/api/offline/receipts/:id?companyBranchId=N`. Devuelve `null` **sólo** para 404 `OFFLINE_RECEIPT_NOT_FOUND`; un 404 genérico/ruta ausente es error y no autoriza replay.
- `offlineDocument({operationId,scope,stepId?,sha256}, LocalPhoto)` → POST `/api/offline/documents`, multipart `files` + `metadata` JSON. Una operación/UUID por archivo (lote atómico local, confirmación independiente). El servidor debe comprobar SHA-256 y usar idempotencia por operación+principal+scope+payload.
- Recibo `{operationId,state:"applied"|"conflict"|"rejected"|"needs_review",error?,fileId?}`. Un UUID diferente nunca confirma. Root group sin `workId`; trabajo/paso con ID canónico. Dependencias de recursos locales se resuelven después de creación; jamás se envía `local-*` al upstream.

`pending`, `syncing`, `applied`, `blocked`, `auth_required`, `needs_review`, `conflict` se conservan. Crash en syncing vuelve a consulta recibo (creación repite mismo UUID). 401 pausa todo; 403/404/validación se mantienen bloqueados. Conflictos/rechazos requieren revisión manual: no hay solucionador/merge/export en UI, ni se sobrescribe el servidor. Endpoints ausentes no caen en métodos legacy no idempotentes. Si el backend pudo ejecutar un efecto pero no persistió su recibo terminal, retiene `needs_review` y no ejecuta ese efecto de nuevo; no se promete exactamente una vez global.

Un GET `applied` no demuestra igualdad del hash: el motor reenvía el POST idéntico, incluidos los bytes propios para documentos, antes de confirmar. GET conflict/needs_review/rejected no autoriza POST. `MOBILE_SYNC_OPERATION_REUSED`, tanto recibo como HTTP 409, permanece en `needs_review` y no admite retry ni confirmación posterior por GET. `MOBILE_SYNC_IN_PROGRESS` mantiene `pending`, UUID/payload intactos y espera durable mínima de cinco segundos, también frente al botón de retry. El arranque y reconexión consultan `connectivity.current()` y reintentan `me` aunque `snapshot.online` sea falso.

### Recuperación selectiva de documentos, 10-09-2026

Corrección posterior: `resolveDocumentScope` es una proyección exclusiva de envío. Mantiene `resolveScope` para caché/UI y adjuntos raíz, pero completa `workId` en grupos directos válidos (`direct-N`/`direct-np-N`). Para creaciones locales exige resultado aplicado, tipo/sucursal coincidentes e ID de trabajo igual al sufijo del grupo. Mantenimiento/externa raíz no se convierten en hijos.

Se recupera además el `OFFLINE_DOCUMENT_UNEXPECTED_ERROR` histórico sólo en documentos raíz directos, sin paso ni recibo, con dependencia/padre consistente. El error nuevo genérico es `OFFLINE_DOCUMENT_SUBMISSION_FAILED` y no reactiva esa reparación. El cliente HTTP diagnostica metadata inválida antes del multipart con `OFFLINE_DOCUMENT_INVALID_METADATA`, en lugar de dejar escapar Zod como error genérico.

Dentro del lease se recupera sólo `kind=document`, `status=needs_review`, sin `receipt` y `lastError=OFFLINE_SYNC_UNEXPECTED_RESPONSE`. Pasa a pending con marcador `OFFLINE_DOCUMENT_RECOVERY_PENDING`; conserva todos los campos inmutables. La identidad se revalida antes de consultar/enviar. GET terminal detiene; GET applied sigue exigiendo POST idéntico. No hay reset global ni nueva UUID.

Antes de cada POST de documento son obligatorios `fileStore.fingerprint`, namespace, reserva/tamaño y SHA-256 coincidentes. En web se vuelve a leer y verificar el blob persistido antes de reutilizar su URL: resolver la misma foto concurrentemente no revoca la copia ya abierta o en envío. Un documento no se confirma sin `fileId` positivo válido. Un error desconocido nuevo se clasifica `OFFLINE_DOCUMENT_SUBMISSION_FAILED` y queda detenido, evitando recuperar indefinidamente el marcador antiguo.

Multipart nativo: [../infrastructure/photos.ts](../infrastructure/photos.ts) fija `name`/`type` sobre la instancia Expo `File`, sin renombrar sus bytes propios. La implementación instalada de Expo 57 ignora el tercer argumento de nombre para ese tipo y la copia UUID no tiene extensión para inferir MIME. Pruebas con el serializador instalado comprueban metadatos y bytes; no sustituyen un teléfono físico.
